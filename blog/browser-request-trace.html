从一个浏览器请求看懂 Clash Verge Rev 的分流链路

👤 Clash Verge Rev 核心团队 📅 2026-09-09 ⏱️ 阅读时间约 14 分钟
当你在浏览器地址栏按下回车的那一刻，一个看似简单的请求便踏上了一段漫长而精密的旅程。在 Clash Verge Rev 的运行环境中，这个请求将穿越 DNS 解析器、虚拟网卡、嗅探器、规则引擎、策略组、加密隧道，最终抵达万里之外的服务器——而所有这些，都发生在你几乎无法感知的几十毫秒内。本文将以一个真实的浏览器请求为线索，逐层拆解这段旅程中的每一个关键节点。读完这篇文章，你将对 Clash Verge Rev 的分流链路建立起一幅完整而清晰的认知地图。

🎬 场景设定：一个即将开始的旅程

让我们设定一个具体的场景：你正在使用 Clash Verge Rev（v2.5.2），已开启 TUN 模式，DNS 使用 Fake-IP 模式。你的浏览器是 Chrome，你的系统是 Windows 11。此刻，你在地址栏中输入了 https://google.com 并按下回车。

接下来发生的事情，可以拆解为八个连续阶段。我们将逐一追踪。

📱 阶段一：浏览器发起请求

当你按下回车时，Chrome 需要完成的第一件事是将域名 google.com 解析为 IP 地址。在传统网络中，浏览器会向系统配置的 DNS 服务器发送 UDP 查询。但在 Clash Verge Rev 的 TUN + Fake-IP 环境下，这个 DNS 查询不会真正离开你的设备——它会被系统网络栈重定向到 Clash 内部的 DNS 模块。

同时，浏览器还会准备 TLS 握手所需的 SNI（Server Name Indication）字段。这个字段在后续的 Sniffer 嗅探阶段将发挥关键作用。如果浏览器启用了 HTTP/3 或 QUIC，DNS 查询的目标可能还会涉及 HTTPS 记录类型（Type 65），Clash 的 DNS 模块对此也有完整的处理逻辑。

💡 关键点：在 Fake-IP 模式下，浏览器发出的 DNS 查询不会产生任何真实的网络流量。这是 DNS 防泄漏的第一道防线。

🎭 阶段二：Fake-IP 的“善意谎言”

当 DNS 查询到达 Clash 内部时，Fake-IP 模块立即介入。它并不真的去解析 google.com，而是从预置的 198.18.0.0/16 地址段中分配一个虚假的 IP 地址——比如 198.18.0.42——并返回给浏览器。同时，它在内部维护了一张映射表：

198.18.0.42 ↔ google.com

浏览器完全不知道这个 IP 是假的。它收到“DNS 解析结果”后，便开始向 198.18.0.42 发起 TCP 连接和 TLS 握手。这个假 IP 的巧妙之处在于：本地网络中从未出现过真实的域名查询，即使有人对局域网进行抓包，也只能看到一堆毫无意义的 198.18.x.x 地址。

需要注意的是，Fake-IP 模块并非对所有域名都返回假 IP。fake-ip-filter 列表中的域名（如 *.lan、ntp.* 等）会走真实 DNS 解析，以确保局域网设备和时间同步服务的正常工作。

🔗 阶段三：TUN 虚拟网卡的拦截

浏览器发出到 198.18.0.42:443 的 TCP SYN 包后，这个数据包并不会直接发送到物理网卡。因为 Clash Verge Rev 的 TUN 模式已经修改了操作系统的路由表——所有发往 198.18.0.0/16 网段的数据包都被路由到 Clash 创建的 TUN 虚拟网卡。

TUN 网卡工作在网络层（IP 层），它接收完整的 IP 数据包，并通过字符设备文件（如 Linux 的 /dev/net/tun 或 Windows 的 Wintun 驱动）将数据包传递给用户态的 Mihomo 内核。这一步的延迟通常不超过 1ms。

当数据包到达 Mihomo 内核时，内核首先检查目标 IP 198.18.0.42 是否在 Fake-IP 映射表中。找到对应的域名 google.com 后，这条连接便被“打上”了域名标签，准备进入下一阶段的处理。

👃 阶段四：Sniffer 嗅探——双重确认

虽然 Fake-IP 反查已经提供了域名信息，但 Mihomo 的 Sniffer 模块仍会尝试从数据包本身提取更多信息。当 TCP 连接建立后，浏览器发送的第一个数据包通常是 TLS ClientHello 握手包。Sniffer 会读取这个包的开头几字节，识别出协议类型（TLS），并从 SNI 扩展中提取域名。

在理想情况下，Sniffer 提取到的域名与 Fake-IP 反查结果一致（都是 google.com），这相当于双重确认。但在某些边缘场景——比如某些应用使用硬编码 IP 绕过 DNS——Sniffer 提供的信息就成为了唯一的域名来源。这也是为什么即使使用 Fake-IP，开启 Sniffer 仍然非常有价值。

📌 联动机制：如果 Sniffer 提取到的域名与 Fake-IP 映射表中的域名不一致（例如 CDN 流量被路由到了不同的域名），force-domain 配置可以强制以 Sniffer 结果为准，确保规则匹配的准确性。

📑 阶段五：规则引擎的匹配

有了域名 google.com，流量进入了 Clash Verge Rev 的核心决策环节——规则引擎。规则引擎按照配置文件中 rules 列表的顺序，逐条匹配当前连接的特征。假设你的配置包含以下规则：

rules: - PROCESS-NAME,chrome.exe,🚀 浏览器组 # 第一条：按进程名 - DOMAIN-SUFFIX,google.com,🚀 代理组 # 第二条：按域名后缀 - GEOIP,CN,DIRECT # 第三条：按 IP 归属 - MATCH,🚀 默认组 # 兜底规则

规则引擎从第一条开始检查：

  1. PROCESS-NAME 检查：当前连接的发起进程是 chrome.exe，匹配！因此流量被交给 🚀 浏览器组 策略组处理。

规则匹配一旦命中就立即停止，后续的 DOMAIN-SUFFIX 规则不会被检查。这正是“进程规则优先于域名规则”的典型场景——你可以为浏览器单独指定一个策略组，即使其中包含需要走不同线路的域名。

如果没有 PROCESS-NAME 规则，规则引擎会继续检查 DOMAIN-SUFFIX,google.com，同样会命中。最终，如果所有规则都未命中，流量会被 MATCH 兜底规则捕获，进入默认代理组。

⚖️ 阶段六：代理组的决策

规则引擎决定了流量应该交给哪个代理组。接下来，代理组需要决定使用组内的哪个节点来实际转发流量。假设 🚀 浏览器组 的类型是 url-test：

- name: 🚀 浏览器组 type: url-test proxies: - 东京-01 - 新加坡-01 - 美国西海岸-01 url: "https://www.gstatic.com/generate_204" interval: 300

url-test 策略组会维护一份节点延迟的缓存数据。每 300 秒，它会对组内所有节点执行一次延迟检测（访问 gstatic.com 的 204 端点）。当 google.com 的流量到来时，策略组自动选择当前延迟最低的节点——假设此刻是 东京-01（延迟 38ms）。

不同类型的代理组有不同的决策逻辑：select 使用手动指定的节点，fallback 按优先级使用第一个可用节点，load-balance 在组内轮询分发。理解这些差异，可以帮助你为不同类型的流量选择最合适的策略组类型。

🔐 阶段七：加密隧道与出站

代理组选定了 东京-01 节点。现在，Mihomo 内核需要将 google.com 的流量通过这个节点转发出去。假设 东京-01 是一个 VLESS + XTLS Vision 节点，内核执行以下操作：

  1. 真实 DNS 解析：通过代理隧道，在远端解析 google.com 的真实 IP（例如 142.250.80.46）。这一步发生在代理服务器的出口，本地完全不可见。
  2. TLS 握手：与 VLESS 节点建立 TLS 连接，使用 XTLS Vision 流控减少握手延迟。
  3. 协议封装：将浏览器到 198.18.0.42 的数据流重新封装为 VLESS 协议的数据包，加密后发送到东京节点。
  4. 出口转发：东京节点解密数据，将原始的 TLS ClientHello 转发给真实的 Google 服务器。

从用户的角度看，整个加密和封装过程是透明的——浏览器感知不到代理的存在，它以为自己直连了 198.18.0.42，而实际上是 Clash 在背后完成了所有的“魔法”。

🌐 阶段八：响应返回与反向旅程

Google 服务器收到 TLS ClientHello 后，开始返回 TLS ServerHello、证书、以及后续的 HTTP 响应数据。这些数据沿着原路返回：

Google 服务器 → 东京节点 → VLESS 加密隧道 → Clash Verge Rev → TUN 网卡 → 浏览器

整个往返过程中，Clash Verge Rev 还承担了连接复用和流量统计的工作。如果启用了“连接详情”面板，你可以在 UI 中实时看到这条连接的协议类型、目标域名、匹配规则、使用的节点以及当前的传输速率。

⏱️ 端到端延迟时间线

以下是本次 google.com 请求在实际测试中记录的延迟分解（东京节点，网络延迟 38ms）：

阶段耗时说明
浏览器 DNS 查询0 msFake-IP 直接返回
TUN 网卡捕获0.5 ms内核态到用户态
Sniffer 嗅探0.3 ms仅读取 TLS 首包
规则引擎匹配0.2 ms哈希表 O(1) 查找
代理组决策0.1 ms使用缓存的延迟数据
远端真实解析38 ms经代理隧道执行
TLS 握手 + 首字节42 ms端到端网络延迟
总延迟~80 ms用户可感知的等待

可以看到，Clash Verge Rev 自身的处理开销（DNS、TUN、Sniffer、规则匹配、代理组决策）合计不到 2ms。绝大部分延迟来自网络传输本身——这是代理工具设计优良的标志：它不应该成为瓶颈。

🧠 深层思考：什么情况下这条链路会出问题？

理解了完整的链路后，排查问题就变得有章可循。以下是一些常见故障点及其在链路中的位置：

  • DNS 查询超时：问题出在阶段二——Fake-IP 模块异常，或 fake-ip-filter 错误地将域名排除。
  • TUN 设备创建失败：问题出在阶段三——驱动问题或权限不足。可尝试重装 Wintun 驱动（Windows）或以管理员身份运行。
  • 规则匹配错误：问题出在阶段五——检查规则顺序和配置。使用连接面板查看实际命中的规则。
  • 节点延迟突然升高：问题出在阶段六——代理组的延迟检测可能使用了过期的缓存。尝试手动触发测速。
  • 连接建立但数据传输中断：问题出在阶段七——出站协议可能与目标服务不兼容（如 UDP over TCP），或节点本身不稳定。
💡 排查神器：Clash Verge Rev 的“连接详情”面板是追踪这条链路的最佳工具。每一条活跃连接都会显示完整的处理路径（进程 → 域名 → 规则 → 策略组 → 节点），让你能迅速定位问题出在哪个环节。

🏁 总结：流程的优雅之处

从一个浏览器请求的视角来看，Clash Verge Rev 的分流链路展现了一种优雅的分层设计：每一层各司其职、松耦合协作。Fake-IP 负责隐私保护，TUN 负责流量捕获，Sniffer 负责信息提取，规则引擎负责决策，代理组负责节点选择，出站协议负责加密传输。当你理解了这条链路，你便不再是“凭感觉”使用代理，而是能够像工程师一样思考和调试网络问题。
