Clash Verge Rev 进程名匹配深度指南：精准控制每个应用的代理行为

👤 Clash Verge Rev 核心团队 📅 2026-07-14 ⏱️ 阅读时间约 11 分钟
大多数代理规则只关心“目标地址”，比如根据域名或 IP 判断流量该走直连还是代理。但如果你想让 Steam 下载走直连而 Epic Games Store 走代理，或者让 VS Code 的远程开发流量走高速节点，而让浏览器的普通流量走日常代理——仅凭域名规则很难做到。Clash Verge Rev 的 PROCESS-NAME 规则为你打开了这扇门：它允许你根据发起网络连接的应用程序进程名来精确匹配流量。本文将带你从基础到高级，掌握这项强大但被低估的规则编写技巧。

📘 基础语法：一条规则搞定一个应用

PROCESS-NAME 规则的写法与域名规则几乎一致，唯一不同的是匹配对象变成了进程名。它的基本格式是：

PROCESS-NAME, <进程名>, <策略组>

例如，让 curl 命令的流量走代理：

- PROCESS-NAME, curl, 🚀 代理

让 Windows 上的微信直连：

- PROCESS-NAME, WeChat.exe, DIRECT

进程名是大小写敏感的，必须与操作系统中实际运行的可执行文件名完全一致。在 Windows 上通常带有 .exe 后缀，而在 macOS 和 Linux 上通常没有后缀。

⚠️ 关键提醒：PROCESS-NAME 规则只有在 TUN 模式 下才能生效。如果你使用的是系统代理模式，流量来源是系统代理服务本身，而不是原始应用，因此进程名始终是 Clash 客户端自身。要发挥 PROCESS-NAME 的全部威力，请确保 TUN 模式已开启。

🔍 找到准确的进程名：三个平台的实战方法

错误的进程名是 PROCESS-NAME 规则失效的最常见原因。下面介绍如何在不同操作系统上精准获取应用的进程名。

Windows：使用任务管理器或 PowerShell

打开任务管理器（Ctrl+Shift+Esc），在“详细信息”标签页中可以看到所有进程的 名称 列。右键点击列标题 → “选择列”，确保“进程名称”已勾选。你需要的是 chrome.exe、steam.exe 这样的名称，而不是“Google Chrome”这样的显示名称。

或者使用 PowerShell 命令：

Get-Process | Select-Object ProcessName

macOS：使用活动监视器或终端

打开“活动监视器”，在“CPU”标签页中查看“进程名称”列。或者通过终端更精确：

ps -eo comm | sort -u

注意 macOS 的进程名通常不包含路径，例如 Google Chrome 的进程名是 Google Chrome（中间有空格，需要引号包围或使用通配符，见后文）。

Linux：使用 ps 或 htop

ps -e -o comm= | sort -u

Linux 进程名通常与可执行文件名相同，例如 firefox、steam、code（VS Code）。

🎮 实战案例集：让应用各走各路

案例一：游戏平台分流

Steam 下载通常不限速，而且国内有完美世界代理的 CDN，走直连更快。但 Epic Games Store 的某些更新源需要代理。可以这样写：

- PROCESS-NAME, steam.exe, DIRECT - PROCESS-NAME, EpicGamesLauncher.exe, 🚀 代理

案例二：开发工具单独路由

VS Code 的远程开发扩展需要低延迟连接，而本地终端只需要跟随系统规则。可以将 VS Code 和终端进程区分：

- PROCESS-NAME, Code.exe, 🚀 开发专线 - PROCESS-NAME, WindowsTerminal.exe, DIRECT - PROCESS-NAME, wsl.exe, DIRECT

案例三：浏览器分身术

你可能希望 Chrome 的日常浏览走代理，但 Firefox 用于内网办公直连：

- PROCESS-NAME, chrome.exe, 🚀 代理 - PROCESS-NAME, firefox.exe, DIRECT

案例四：容器与虚拟机

Docker 容器的网络请求通常经由 dockerd 或 vpnkit 进程，因此可以通过匹配这些进程来控制整个 Docker 网络的代理行为：

- PROCESS-NAME, dockerd, 🚀 代理 - PROCESS-NAME, vpnkit.exe, 🚀 代理
💡 技巧：如果你不确定某个应用的进程名，可以临时将所有规则清空，只留一条 MATCH, 🚀 代理，然后打开 Clash Verge Rev 的“连接”面板，查看目标应用产生的连接，面板上会显示对应的“进程”列，那就是你需要的进程名。

🧩 进阶技巧：通配符、多进程匹配与优先级

通配符支持

PROCESS-NAME 规则支持使用 * 和 ? 通配符，这在进程名包含空格、版本号或不固定后缀时非常有用：

# 匹配所有以 "Google" 开头的进程（Google Chrome、Google Drive 等） - PROCESS-NAME, Google*, 🚀 代理 # 匹配 macOS 上可能的带空格进程名 - PROCESS-NAME, "Google Chrome", 🚀 代理

多进程列表

如果你需要让多个应用共享同一策略，不必为每个进程名单独写一条规则，可以用逗号分隔：

- PROCESS-NAME, chrome.exe, firefox.exe, msedge.exe, 🚀 浏览器组

规则优先级

与所有规则一样，PROCESS-NAME 也遵循从上到下匹配的顺序。建议将更具体的进程规则放在通用域名规则之前，以避免被后者的兜底规则吃掉。例如：

rules: - PROCESS-NAME, steam.exe, DIRECT - DOMAIN-SUFFIX, steampowered.com, 🚀 代理 - MATCH, 🚀 默认代理

在这个例子中，Steam 的所有流量（包括向 steampowered.com 发起的请求）都会被第一条规则捕获并直连，因为 PROCESS-NAME 的优先级高于后面的 DOMAIN 规则。这正是我们想要的效果。

⚡ 与 TUN 模式协同：内核级进程识别

PROCESS-NAME 规则依赖 TUN 模式提供的套接字所有权信息。当流量通过 TUN 虚拟网卡时，Linux/Windows 内核能够在网络栈中记录数据包的来源进程，Mihomo 内核再通过特定接口（如 Linux 的 SO_ORIGINAL_DST 或 Windows 的 WFP）读取这些信息。因此在 TUN 模式下，无论应用使用什么协议、连接到什么 IP，内核都能准确溯源。

在 macOS 上，由于系统限制，进程识别依赖于 utun 接口的辅助信息，准确性略低于 Linux/Windows，但通常足以应对常见场景。

⚠️ 局限：如果应用通过其他代理（如内嵌的 SOCKS5 客户端）发起连接，或者流量经过了另一层 NAT（如 Docker 的桥接网络），进程信息可能会丢失。此时 PROCESS-NAME 规则将无法匹配，流量会降级到后续规则处理。

🧠 性能影响与最佳实践

每条 PROCESS-NAME 规则都需要在连接建立时进行一次进程名查找，这个操作的开销极小（微秒级），通常不会对整体吞吐量产生可感知的影响。但在极少数场景下——例如你有数十条进程规则且同时有数千个短连接——可以考虑以下优化：

  • 合并规则：将多个进程名合并到同一条规则中，减少匹配迭代次数。
  • 使用通配符：一条 PROCESS-NAME, Game*, 🎮 游戏 替代分别列出 game1.exe、game2.exe。
  • 避免过度匹配：不要为每个小工具都创建进程规则。对于那些只需跟随默认策略的应用，不必单独列出，让它们直接落到 MATCH 或最后的域名规则即可。

🔧 常见问题与排查

Q：规则写好了但完全没生效？
A：首先确认 TUN 模式已开启。然后检查进程名是否精确（注意大小写和后缀）。最后在“连接”面板中观察对应连接是否被 PROCESS-NAME 规则命中。
Q：Windows 上带空格的进程名怎么处理？
A：使用双引号包围，如 PROCESS-NAME, "Google Drive", DIRECT。或者使用通配符 PROCESS-NAME, Google*, DIRECT。
Q：某些应用有多个子进程，需要全部列出吗？
A：通常只需匹配主进程即可，因为网络连接一般由主进程发起。但像 Chrome 这样的多进程浏览器，网络请求可能由 chrome.exe 发起（在 Windows 上），所以一个条目就够了。如果发现某些连接未命中，在连接面板中查看具体是哪个子进程发起的，然后补充规则。
Q：进程名规则和域名规则冲突时谁优先？
A：规则列表从上到下顺序匹配，先写谁谁优先。通常建议将进程规则放在域名规则之前，以实现“整应用分流”的目标。

🏁 总结

PROCESS-NAME 规则为你提供了传统域名和 IP 规则无法实现的应用维度控制能力。结合 TUN 模式，你可以轻松实现游戏直连加速、开发工具专属通道、浏览器按需求分流等高级场景。记住三个关键点：开启 TUN 模式、精准获取进程名、合理排列规则优先级，就能让 Clash Verge Rev 真正做到“物尽其用，流尽其路”。
