Clash Verge Rev 规则详解：DOMAIN 与 DOMAIN-SUFFIX 的精准对决

👤 Clash Verge Rev 核心团队 📅 2026-07-27 ⏱️ 阅读时间约 10 分钟
在 Clash Verge Rev 的规则列表中，DOMAIN 和 DOMAIN-SUFFIX 是使用频率最高的两种匹配方式。许多用户在编写配置时，往往会凭感觉选择其中一个，却忽略了它们在匹配逻辑上的本质区别——以及这种区别对分流精度和性能的影响。本文将用大量实例，将这两个看似相似的规则类型放到显微镜下对比，帮助你写出更精准、更高效的代理规则。

📖 基本定义：精确与模糊

从字面意义上看，两者区别明显：

  • DOMAIN：精确匹配一个完整的域名。规则 DOMAIN, google.com, 🚀 代理 只会匹配 google.com 这个域名本身，不会匹配 www.google.com 或 mail.google.com。
  • DOMAIN-SUFFIX：匹配域名后缀，即域名及其所有子域名。规则 DOMAIN-SUFFIX, google.com, 🚀 代理 会匹配 google.com、www.google.com、mail.google.com、a.b.c.google.com 等所有以 .google.com 结尾的域名。

理解这个基本差异后，我们进一步探讨它们在实战中的表现。

🎯 DOMAIN 的独特价值：精确打击

在大多数场景下，DOMAIN-SUFFIX 因其“一次编写，覆盖所有子域名”的便利性而更受欢迎。但 DOMAIN 在某些关键场景中是不可替代的：

场景一：只代理主站，不代理 CDN

某些网站的主站可能需要代理才能访问，但其静态资源 CDN 在国内有节点，直连更快。例如：

- DOMAIN, example.com, 🚀 代理 - DOMAIN-SUFFIX, cdn.example.com, DIRECT

这里如果使用 DOMAIN-SUFFIX, example.com, 🚀 代理，会导致 cdn.example.com 也被代理。通过 DOMAIN 精确锁定主站，再配合另一条 DOMAIN-SUFFIX 让 CDN 直连，可以达到最佳效果。

场景二：避免误伤根域名

某些顶级域名（如 .ai、.io）属于国家/地区顶级域，但同时也是许多网站的实际域名后缀。例如规则 DOMAIN-SUFFIX, ai, 🚀 代理 会让所有 .ai 结尾的域名都走代理，包括一些国内合法的 .ai 网站。这种情况下，应该用 DOMAIN 精确列出需要代理的特定域名。

🌐 DOMAIN-SUFFIX 的优势：泛域名覆盖

绝大多数互联网公司的服务都分布在多个子域名下。以 OpenAI 为例，除了 openai.com，还有 api.openai.com、cdn.oaistatic.com、auth0.openai.com 等。使用 DOMAIN-SUFFIX 可以一次性覆盖所有这些域名，避免遗漏：

- DOMAIN-SUFFIX, openai.com, 🚀 代理 - DOMAIN-SUFFIX, oaistatic.com, 🚀 代理

这种“一对多”的覆盖能力是 DOMAIN 无法做到的。正因如此，在社区维护的 RULE-SET 中，绝大多数条目都采用 DOMAIN-SUFFIX。

🧬 匹配逻辑的细节：. 符号与 TLD 陷阱

一个容易被忽略的细节是，DOMAIN-SUFFIX 匹配时会自动在传入的字符串前添加一个 . 号。这意味着：

  • DOMAIN-SUFFIX, google.com 实际匹配的是 .google.com。
  • 因此它能匹配 www.google.com（因为 www.google.com 包含 .google.com），也能匹配 google.com（内核特殊处理）。

但也正是因为这个机制，写 DOMAIN-SUFFIX, com 会把所有 .com 结尾的域名都匹配进去——这显然不是我们想要的。因此，DOMAIN-SUFFIX 的值至少应该包含二级域名。

⚠️ 常见错误： 将 DOMAIN-SUFFIX 用于顶级域或公共后缀（如 com、co.uk），会导致大量无关联域名被误匹配。建议使用浏览器公共后缀列表（Public Suffix List）作为参考，确保后缀至少为“注册域名”级别。

⚡ 性能差异：DOMAIN 比 DOMAIN-SUFFIX 更快吗？

在 Mihomo 内核中，两种规则都经过了高度优化。DOMAIN 规则被编译为哈希表，查询时间复杂度为 O(1)。DOMAIN-SUFFIX 规则被编译为紧凑的前缀树，查询时间复杂度为 O(log n)，其中 n 是规则数量。

在规则数量较少（< 100 条）的情况下，两者的性能差异几乎无法察觉。当规则数量达到数千条时，DOMAIN 的哈希查找理论上更快，但 DOMAIN-SUFFIX 的前缀树优化也非常出色，实际差异在微秒级别。因此，不必因为性能原因刻意选择 DOMAIN 或 DOMAIN-SUFFIX，应该根据匹配需求来决定。

🧩 最佳实践：DOMAIN 与 DOMAIN-SUFFIX 的组合策略

在实际配置中，我们建议按照以下思路组合使用这两种规则：

  1. 优先使用 DOMAIN-SUFFIX：对于拥有多个子域名的服务（如各大互联网公司），使用 DOMAIN-SUFFIX 一次性覆盖。
  2. 用 DOMAIN 做精确例外：当某个子域名需要不同的分流策略时，用 DOMAIN 精确覆盖。利用规则优先级（先匹配先生效），将 DOMAIN 写在 DOMAIN-SUFFIX 之前。
  3. 避免过度使用 DOMAIN：如果每个子域名都单独写一条 DOMAIN，会导致规则数量爆炸，拖慢配置加载和匹配速度。
  4. 善用 RULE-SET：将大量重复性的 DOMAIN-SUFFIX 规则放入远程 RULE-SET，只在本地区配置少量 DOMAIN 例外。
# 推荐写法：DOMAIN 精确例外在前，DOMAIN-SUFFIX 泛域名在后 rules: - DOMAIN, static.example.com, DIRECT - DOMAIN-SUFFIX, example.com, 🚀 代理

❌ 常见错误与纠正

错误 1： 想代理 www.google.com，写成了 DOMAIN, www.google.com，结果 google.com 本身不走代理。
纠正： 如果需要同时代理主域和子域，应使用 DOMAIN-SUFFIX, google.com。
错误 2： 使用 DOMAIN-SUFFIX, api.openai.com 以为只会匹配 api.openai.com，实际却匹配了 v1.api.openai.com。
纠正： 这其实不是错误，而是 DOMAIN-SUFFIX 的预期行为。如果只想匹配 api.openai.com，应该使用 DOMAIN, api.openai.com。
错误 3： 在一个大型配置中混用数百条 DOMAIN 和 DOMAIN-SUFFIX，导致规则顺序混乱，匹配结果不可预期。
纠正： 保持规则列表的结构清晰——将 DOMAIN 例外放在最前面，然后是 DOMAIN-SUFFIX 泛域名，最后是 GEOIP 和 MATCH。

🏁 总结

DOMAIN 和 DOMAIN-SUFFIX 并非“谁更好”的关系，而是分工不同的搭档。DOMAIN 擅长精确打击，DOMAIN-SUFFIX 擅长泛域名覆盖。理解它们的匹配逻辑，并按照“例外在前、泛域名在后”的原则组织规则，是写出高效、可维护的 Clash Verge Rev 配置的关键。如果你对规则编写还有更多疑问，欢迎在 GitHub Discussions 中与我们交流。
