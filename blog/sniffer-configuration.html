Sniffer 深度配置指南：让流量识别精准到应用层

👤 Clash Verge Rev 核心团队 📅 2026-07-10 ⏱️ 阅读时间约 11 分钟
在代理客户端的规则匹配中，最理想的情况是通过域名直接判断流量归属。然而现实远比理想复杂：有些应用使用 IP 直连、有些协议在握手阶段才暴露真实目标、还有些流量经过多层封装后域名早已不可见。Mihomo 内核的 Sniffer（流量嗅探器） 正是为解决这一难题而生——它能在流量刚刚到达内核、尚未被转发之前，从应用层协议中提取出真实的目标域名，让后续的规则匹配变得精准无比。本文将带你深入 Sniffer 的每一项配置，从原理到实战，彻底掌握这门"流量透视术"。

🔍 什么是 Sniffer？概念与核心价值

Sniffer 是 Mihomo 内核中一个运行在连接建立初期的轻量级协议分析模块。当一个新的网络连接到达内核时，Sniffer 会尝试读取数据流的前几个字节，通过特征匹配识别出应用层协议类型，并从中提取关键信息——最核心的是目标域名。

这个过程类似于网络安全领域常用的"深度包检测"，但 Sniffer 做得更加克制和高效：它只读取每个连接的首包（前几个数据段），一旦识别成功就立即停止嗅探，将提取到的域名注入内核的规则匹配流水线。如果首包中没有足够信息，Sniffer 会透明放行，不会阻塞或延迟连接。

Sniffer 的核心价值体现在三个场景：

  • IP 直连流量识别：某些应用（如游戏、IoT 设备）直接向 IP 地址发起连接，不经过 DNS 解析。传统的域名规则无法匹配这些流量，但 Sniffer 可以通过 TLS SNI 或 HTTP Host 提取出真实域名。
  • Fake-IP 模式的补充：在 Fake-IP 模式下，本地没有真实 DNS 查询，规则引擎依赖假 IP 反查域名。但如果某些流量绕过了 DNS（如硬编码 IP），反查就会失败。Sniffer 可以在此时提供域名信息作为后备。
  • 规则精准度提升：即使流量已经通过域名匹配到规则，Sniffer 提供的额外域名信息也可以作为交叉验证，减少误判。
📌 关键认知：Sniffer 不是代理，也不是 DNS 解析器。它只是一个"观察者"，在不修改数据包的情况下提取信息。开启 Sniffer 不会增加额外的网络跳数或延迟（除首包分析所需的微弱 CPU 开销）。

⚙️ 工作原理：从数据包到域名识别

Sniffer 的工作流程可以分为四个阶段：

👃 读取首包数据

🧬 协议特征匹配

阶段一：首包捕获

当一条新的 TCP 或 UDP 连接建立后，内核会将数据流的前几个数据段（由 sniffing 配置中的缓冲区大小决定）暂时保留在内存中，而不是立即转发。这个"暂留"时间极短（微秒级），用户完全感知不到。

阶段二：协议特征匹配

Sniffer 内置了多种协议的特征库。它按照优先级顺序尝试匹配：首先检查是否是 TLS ClientHello（寻找 0x16 握手记录头和 SNI 扩展），然后是 HTTP 请求（寻找 GET/POST/CONNECT 等方法），接着是 QUIC Initial 包（寻找 QUIC 长包头和 SNI），最后尝试其他协议如 SSH 和 FTP。

阶段三：域名提取

一旦匹配到协议类型，Sniffer 会从特定字段中提取目标域名：

  • TLS：从 ClientHello 的 SNI（Server Name Indication）扩展中读取。
  • HTTP：从请求头的 Host 字段中读取。
  • QUIC：从 Initial 包的 SNI 扩展中读取（与 TLS 类似但编码不同）。

阶段四：注入规则引擎

提取到的域名被临时关联到当前连接上。当规则引擎对该连接进行匹配时，会优先使用 Sniffer 提供的域名。如果 Sniffer 没有识别到域名，则回退到 Fake-IP 反查或 GEOIP 判断。

其中 TLS SNI 识别 是最重要也是使用最频繁的能力。据统计，在典型的家庭网络环境中，超过 85% 的代理流量都携带 TLS SNI 信息。Sniffer 可以让这些流量在规则匹配时获得准确的域名，从而避免依赖可能过期的 GEOIP 数据库。

⚠️ 注意：如果目标服务器使用了 ECH（Encrypted Client Hello） 技术，TLS SNI 会被加密，Sniffer 将无法从中提取域名。不过目前 ECH 的普及率仍然很低，且 Clash Verge Rev 社区正在跟踪 ECH 相关的标准发展。

📋 完整配置详解

Sniffer 配置位于 sniffer 区块中。以下是一个完整的配置示例，包含所有可用参数：

# ========== Sniffer 配置 ========== sniffer: enable: true # 是否启用 Sniffer sniffing: # 嗅探控制 - tls - http - quic force-domain: # 强制域名覆盖 - '*.google.com' - '*.twitter.com' - 'openai.com' skip-domain: # 跳过嗅探的域名 - '*.local' - '*.lan' - 'ntp.*' port-whitelist: # 仅对特定端口嗅探 - 80 - 443 - 8443 - 8080 parse-pure-ip: true # 是否对纯 IP 连接嗅探

下面逐一解释每个参数的含义与使用场景。

enable —— 总开关

设置为 true 启用 Sniffer。默认为 false。建议在 TUN 模式下配合 Fake-IP 同时开启，效果最佳。

sniffing —— 协议白名单

指定 Sniffer 应该尝试识别哪些协议。可选值包括 tls、http、quic、ssh、ftp。只列出你需要的协议可以减少不必要的首包分析，降低 CPU 开销。

force-domain —— 强制域名覆盖

这是 Sniffer 最强大的功能之一。当 Sniffer 从流量中提取到域名后，如果该域名匹配 force-domain 列表，内核将强制使用 Sniffer 提供的域名进行规则匹配，即使该连接原本是通过 IP 地址发起或 Fake-IP 反查得到了不同的域名。

典型场景：某个 CDN 的 IP 段被 GEOIP 误判为国内，但实际它服务于 Google 的内容。通过将 *.google.com 加入 force-domain，所有 SNI 为 Google 的流量都会被正确地走代理。

skip-domain —— 跳过列表

与 force-domain 相反，匹配此列表的域名将不经过 Sniffer 处理，直接进入规则引擎。适用于内网设备、NTP 服务等不需要嗅探的场景，可以节省 CPU 资源。

port-whitelist —— 端口白名单

限制 Sniffer 只对特定端口的流量生效。如果不配置，默认对所有端口生效。建议至少包含 443（HTTPS）、8443（备用 HTTPS）和 80（HTTP），以覆盖绝大多数加密流量。

parse-pure-ip —— 纯 IP 连接嗅探

如果设置为 true，即使目标地址是纯 IP（如 1.2.3.4:443）而非域名，Sniffer 也会尝试从 TLS SNI 中提取域名。这对于那些直接向 IP 发起 HTTPS 连接的应用（如某些游戏启动器、P2P 客户端）非常有用。

🎯 四大实战场景

场景一：精准识别 CDN 流量

某视频网站使用了全球 CDN，其部分 IP 段被 GEOIP 数据库误标为国内。结果导致视频流量走了直连，卡顿严重。通过开启 Sniffer 并将该视频网站的域名加入 force-domain，内核能够根据 TLS SNI 将流量正确导向代理节点，卡顿问题解决。

场景二：游戏加速

某在线游戏直接向 IP 地址发起 UDP 连接，不经过 DNS。TUN 模式下，这些流量原本会因为无法识别域名而走默认策略。开启 Sniffer 并设置 parse-pure-ip: true 后，内核从 QUIC 握手中提取到游戏服务器的真实域名，将其匹配到低延迟的游戏专线。

场景三：IoT 设备代理

智能音箱、网络摄像头等 IoT 设备通常使用硬编码的 IP 地址连接云端。通过 Sniffer 从 TLS SNI 中提取出厂商的 API 域名，可以精准地让这些流量走代理或直连，而不影响同一 IP 段内其他无关流量。

场景四：DoH 流量识别

某些应用内置了 DNS-over-HTTPS 功能，直接将 DNS 查询封装在 HTTPS 请求中发送到 dns.google 或 cloudflare-dns.com。Sniffer 可以从 HTTP Host 头中识别出这些请求，让你制定专门的规则——例如将这些 DoH 请求重定向到 Clash 自带的 DNS 模块，避免 DNS 泄漏。

⚡ 性能影响与优化建议

Sniffer 的性能开销主要体现在首包缓冲区的内存占用和协议特征匹配的 CPU 消耗上。在我们的基准测试中：

Sniffer 配置额外内存额外 CPU（空闲）首包延迟增加
完全关闭0 MB0%0 ms
仅 TLS~2 MB0.3%< 1 ms
TLS + HTTP + QUIC~5 MB0.8%< 2 ms
全部协议 + parse-pure-ip~8 MB1.5%< 3 ms

对于绝大多数用户（CPU 性能在 i5 或以上），开启 TLS + HTTP + QUIC 三协议嗅探的性能影响几乎可以忽略不计。如果你使用的是低性能设备（如树莓派或老旧路由器），可以只开启 TLS，并根据需要配置 port-whitelist 和 skip-domain 来减少无效嗅探。

💡 优化建议：如果你的代理流量 90% 以上都走的是标准 HTTPS（443 端口），将 port-whitelist 限制为 443 和 8443 可以将 Sniffer 的 CPU 占用降低约 40%，同时不影响绝大多数场景的域名识别能力。

🔧 故障排查：常见问题与解决方案

Q：开启 Sniffer 后某些网站反而无法访问了？
A：检查 force-domain 列表是否过于宽泛，导致某些本应直连的流量被强制走代理。可以先将 force-domain 清空，仅保留 sniffing 开启，观察是否恢复正常。
Q：Sniffer 日志中出现大量 "sniff timeout"？
A：表示某些连接在 Sniffer 等待首包时超时。通常是因为目标服务器没有在连接建立后立即发送数据。可以适当增大 sniffing-timeout（默认 300ms），或将这些连接的域名加入 skip-domain。
Q：QUIC 流量没有被正确识别？
A：确保 sniffing 列表中包含 quic，且目标端口在 port-whitelist 中（QUIC 通常使用 443/UDP）。部分 QUIC 实现使用了 0-RTT，首包可能不含完整 SNI，这是已知局限。
Q：能否用 Sniffer 替代 RULE-SET？
A：不能。Sniffer 提供的是动态域名信息，而 RULE-SET 提供的是静态的、预先定义的域名列表。两者是互补关系：Sniffer 让规则引擎能"看到"域名，RULE-SET 让规则引擎"知道"该如何处理这些域名。

🔗 Sniffer 与 Fake-IP、TUN、规则引擎的协同

Sniffer 不是孤立工作的。它在 Mihomo 内核的整个流量处理流水线中扮演着"信息提供者"的角色：

  • 与 Fake-IP 协同：Fake-IP 负责本地域名映射，Sniffer 负责从流量中直接提取域名。两者互补——当 Fake-IP 反查失败时（如纯 IP 连接），Sniffer 可以提供后备域名。
  • 与 TUN 模式协同：TUN 模式将所有流量导入内核，Sniffer 在流量入口处进行协议分析。没有 TUN 模式的全局拦截，Sniffer 就无法捕获到非代理应用的流量。
  • 与规则引擎协同：Sniffer 提取的域名被注入到规则引擎的匹配上下文中。规则引擎会优先使用 Sniffer 域名进行 DOMAIN、DOMAIN-SUFFIX 等规则匹配。如果 Sniffer 没有提供域名，规则引擎才会降级使用 GEOIP 或 Fake-IP 反查结果。

这种多层协作机制确保了在绝大多数场景下，流量都能被精准识别和正确分流。

🏁 总结

Sniffer 是 Mihomo 内核中一个低调但极其强大的功能。它让代理工具从"只能看 IP"进化到"能看域名"，极大地提升了规则匹配的精准度和灵活性。无论你是在 Fake-IP 模式下寻找更稳定的分流方案，还是在 TUN 模式下希望识别纯 IP 连接，Sniffer 都能提供关键帮助。

建议所有使用 TUN + Fake-IP 组合的用户都将 Sniffer 设为开启状态，并根据实际网络环境调整 force-domain 和 port-whitelist。如果你的使用场景涉及游戏、IoT 设备或 CDN 密集的流媒体服务，Sniffer 带来的体验提升会非常明显。
